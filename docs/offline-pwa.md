# Phase 4 — offline camera harness

Codex implementation, 2026-11-03. Scope: the lead-owned camera harness, its static build and tests. Genuine Kiro specs/metadata, teammate app UIs and compiled SDK contracts remain unchanged. User-reported physical Phase 3 results are recorded separately in [evidence](evidence/2026-11-03-user-reported-phase-3.md); they do not certify this Phase 4 build.

## Behavior and data preservation

The selected application is saved under `localStorage['carrysync-camera.application.v1']`. Only `field-ledger` and `quiz-relay` are accepted; invalid/missing preferences fall back to FieldLedger. A valid `?app=` launch override is consumed once and saved, so subsequent dropdown changes survive reload. Disabled preference storage produces an understandable warning without disabling the SDK. App-bound clients still use the existing `[app+id]` IndexedDB partition; switching never copies or clears records. The existing `carrysync-camera-v1` database name, schema and device identity are unchanged.

The production build registers `sw.js` within the current directory (GitHub Pages `/carrysync-kit/` or a standalone root). `manifest.webmanifest` has relative `id`, `scope`, `start_url` and original 192/512 PNG icons. Browser **Install app** / **Add to Home Screen** is optional for offline browser navigation; installation UI depends on the browser. Vite development mode deliberately does not register a worker; use `npm run build:camera && npm run build:harness && npm run preview:camera` for offline tests.

`scripts/build-offline.mjs` enumerates the complete finished Vite artifact: HTML (including inline CSS), all JS including the lazy decoder, WASM, notices, public metadata, manifest and icons. Any future emitted CSS/assets are included automatically. Every essential resource has a SHA-256 integrity value; worker source plus resource bytes determine a deterministic cache version. `verify-static-harness.mjs` checks completeness/integrity and rejects unexpected files/credential patterns. No external CDN, new dependency or deployment secret is required; the existing CSP remains in force.

Worker installation atomically caches that exact allowlist with integrity-checked same-origin requests. A missing/corrupted asset fails installation and removes the incomplete new cache. HTTP cache reuse is bypassed. Navigations to the scope root or `index.html` use its cached HTML, ignoring query strings for the cache key. Essential assets use the same version's cache. Other URLs and non-GET requests are never cached. No arbitrary runtime cache, records, UUID, personal payloads, generated QR data, camera frames, form submissions or API responses are stored by the worker.

`Ready for Offline Use` requires an activated worker controlling the page, a matching current script entry, and a worker-side check that **every essential resource** exists in its cache. Merely registering a worker or keeping a page open cannot produce readiness. Status is rechecked on navigation, visibility/connection changes and retry. Missing/blocked/evicted storage revokes readiness. Reconnect and press **Check / retry offline preparation** to repair missing allowlisted resources; integrity checks prevent repair from mixing old resources with a different deployed build. If the old build can no longer be repaired, close all tabs and reopen online to install the current release. Existing IndexedDB records remain intact.

## Updates

There is no forced `skipWaiting`, reload or storage clearing. A new release downloads a separate versioned cache and waits while any old controlled tab/window remains open. The page reports an update is cached. Finish imports, close **all** CarrySync tabs and installed windows, then reopen; activation removes only obsolete `carrysync-camera-shell:<scope path>:` caches. Other caches and all IndexedDB/localStorage data are untouched. A failed update leaves the active version's cache available. Normal navigation/retry checks for worker updates using `updateViaCache: 'none'`.

If a phone still shows the older Phase 3 page, reconnect and reload to obtain the first Phase 4 shell, then wait for readiness. Later updates follow the waiting lifecycle above. **Do not clear site data, uninstall with data removal, unregister workers, rename the DB or rotate the UUID as an update procedure.**

## Verification and limits

`npm run test:browser` includes actual Chrome worker installation/activation, both app preferences/isolation, offline reload, tab reopen, full browser-process close/restart with a retained disk profile and networking disabled **before** navigation, offline QR generation/import, existing records/UUID retention, both app camera decodes using real cached WASM after reload without online decoder warm-up, quota/eviction-style missing-cache checks/repair, failed downloads/integrity, and safe updates/cache cleanup. A local fault server tests worker fetch failures directly (page routing does not intercept worker fetches). `npm run test:live` runs the static + offline suite against the production HTTPS artifact, including cold-profile reopen and synthetic camera tests. These are desktop Chromium results, not real-phone/OS process-kill results.

Offline use requires one successful online preparation in the **same origin and browser profile** with storage retained. First-ever offline visits, private browsing restrictions, browser/OS eviction, cleared site data and storage quota denial cannot be guaranteed. A ready indication is a verified state at check time, not a promise that an OS will never evict data. Android/iOS installation and process termination behavior need actual phone acceptance. Application-level sync/export backups, future schema upgrades and teammate frontend PWA wiring remain separate work. No background sync, push or server data service is added.

References informing lifecycle/update behavior: [Chrome Service Worker lifecycle](https://developer.chrome.com/docs/workbox/service-worker-lifecycle), [W3C lifecycle explainer](https://github.com/w3c/ServiceWorker/blob/main/explainer.md).
